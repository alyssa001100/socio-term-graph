# 负例集

这个目录里的数据**故意写错**，唯一用途是检验 `validate.py` 本身。

校验器说「0 错误」只有在它能抓出错误时才有意义。一个永远返回通过的校验器和没有校验器，结果完全一样。所以这里的做法是：先手工注入已知的违规，再看校验器是否一个不落地报出来。

## 用法

```bash
python3 selftest.py
```

输出：

```
负例集：negative
  注入的规范违反点   64 个
  校验器实际报错     64 条
  命中 64 · 漏检 0 · 误报 0

自检通过：每条注入的违规都被精确命中，且没有多余报错。
```

**漏检** = 某条规范在代码里失效了，校验器抓不到。
**误报** = 出现了预期之外的报错，说明负例数据里有非预期问题，或某条规则过严。

两种情况都会让脚本以退出码 1 结束。

## 新增概念群时为什么还要再验一遍

跨群规则（不得「等同」、每对群上限 5 条）在第 3–6 个群出现之前就已经有负例（N45 / N46）。v7 加群之后仍然补了 N54 / N55 三条，理由不是覆盖率好看，而是这两条规则**最容易被写成只看原来那几对群**——一旦实现依赖了具体的群名，新群之间的违规就会静默放过，而旧负例永远发现不了。同一套规则换一对群再验一次，才是对「规则写在配置上、不是写死在代码里」的真实验证。

N57 测的是配置自身的一致性。它不校验数据，而是往 `schema.yaml` 里注入一个「只在 `clusters` 里出现、没在 `enums.cluster` 里放开」的群——这个群不挂任何术语，所以除它本身之外不会连带污染其它负例，误报数为 0 才说明这条规则既生效、又不会误伤。

## 为什么「标签重复」这类问题只能靠规则

N58 / N59 / N60 注入的三条违规有一个共同点：**看数据完全看不出问题**。取值通顺、长度合规、字段齐全，跑任何字段级校验都是绿的；只有渲染成页面之后才会露出重复——`match` 写「相符之处：……」，页面上就是「相符之处：相符之处：……」。

这类问题的危险不在于难看，而在于**没有任何一条既有规则会失败**。负例集对它的价值也因此更大：注入之后如果没报错，说明规则压根没生效，而不是被别的问题掩盖。N60 还多测一层：`explain` 里写死的「跨群桥接」不只是重复，它是一句可以被 `cluster` 推翻的断言——术语一旦迁去别的概念群，这行前缀就从冗余变成错误，而其它规则只看 `cluster`，永远不会报。

## 编写纪律

1. **除注入点外，其余字段一律填成合规值。** 否则会产生无法归因的噪音，把真正的漏检淹掉。
2. **一处注入对应尽量少的报错。** 例如「缺必填字段」要挑不会被枚举检查二次报错的字段，否则一处注入产生两条报错，清单就要写两条。
3. **注意 YAML 行内映射的标点陷阱。** `where: "TERM-9005.polysemy[1]"` 必须加引号——方括号和英文逗号在 `{...}` 行内映射里是保留字符，不加引号会被解析成别的东西。这个坑本文件自己踩过一次。
